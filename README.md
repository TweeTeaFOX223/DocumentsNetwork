# 📄 DocumentsNetwork  

**DocumentsNetwork** は、クエリ文書の類似文書を検索し、ネットワーク図として可視化するアプリケーションです。  


## 🎯 機能概要  
- クエリに基づいて類似文書を検索  
- 文書間の関連性をネットワークとして可視化  
- 直感的なインターフェースで関係性を把握

## 設定の説明  
クエリ文書をアップロードすると、類似文書をグラフとして可視化します。  
**Visual・Graph・Search** の3項目をそれぞれ1つ選択し、実行してください。  
  
### 1. Visual（グラフ可視化手法）

ノードを2次元空間に配置する際のレイアウトアルゴリズムを選択します。

| 選択肢                   | 説明                                                                           | 特徴                                                             |
| ------------------------ | ------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| **スペクトラル法**       | 隣接ノードの座標が近くなるよう配置する手法                                     | 計算が速いが、ノードが重なりやすく視認性が低下しやすい           |
| **多次元尺度法**         | 高次元空間での複数観点の類似性を保ちながら低次元に射影する手法                 | 全体的な距離構造を反映しやすい                                   |
| **クロスエントロピー法** | 隣接ノードを非隣接ノードより近くに配置するよう交差エントロピーを最小化する手法 | ノードの重なりを抑えやすいが計算コストが高い                     |
| **ばねモデル法**         | 全エッジをばねとみなし、ノード間の最短パス長を自然長として配置する手法         | **推奨**。ノードの重なりが最も少なく、エッジ長のばらつきも小さい |

> **推奨設定：ばねモデル法**
> エッジ長の均一性・ノードの重なりにくさの両面で最も高品質なグラフが得られます。

---

### 2. Graph（グラフ構成法）

文書間のエッジ（繋がり）をどのように構築するかを選択します。

| 選択肢                | 説明                                                                                                     | 特徴                                                                                 |
| --------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **最小全域木（MST）** | コサイン類似度が最大となるエッジを優先的に選び、全ノードを連結する最小本数のエッジでグラフを構成する手法 | エッジ数が少なくツリー状になる。全体構造は把握しやすいが、密な部分構造の視認性は低い |
| **K最近傍法（KNN）**  | 各ノードに対して類似度の高い近傍ノードとのエッジを追加し、グラフ全体が連結になるまで繰り返す手法         | **推奨**。MSTより密なグラフが得られ、類似文書のクラスター構造を視覚的に把握しやすい  |
| **MST-hML**           | MSTを骨格として構築した後、コサイン類似度が特に高いペアのエッジをさらに追加するハイブリッド手法          | MSTの疎さを補いつつ、高類似度の関係を強調できる                                      |

> **推奨設定：K最近傍法**
> クラスター構造や密な類似関係の把握に最も適しています。

---

### 3. Search（検索文書数）

クエリ文書に対して検索する類似文書の件数を選択します。

| 選択肢    | 説明                                                                                         |
| --------- | -------------------------------------------------------------------------------------------- |
| **50件**  | 文書数が少ないためグラフはシンプルになるが、密な部分構造が見えにくい場合がある               |
| **100件** | **推奨**。視認性と情報量のバランスが最も良い                                                 |
| **150件** | やや多めの文書を俯瞰したい場合に使用                                                         |
| **200件** | 多数の文書を一覧できるが、元の文書集合に類似文書が少ない場合は関連性の薄い文書が混入しやすい |

> **推奨設定：100件**
> 文書数が少なすぎると構造が単純すぎ、多すぎると無関係な文書が混入するリスクがあります。100件が最も安定した可視化結果を得られます。

特に理由がない場合は以下の設定をお試しください。

```

Graph   : K最近傍法

```

## グラフの見方

- **赤い大きな丸**：アップロードしたクエリ文書
- **色付きの小さな丸**：検索結果の類似文書（同じ色のノードは同じ「説明語」でクエリに類似していることを示す）
- **グラフ上部の凡例**（例：`● 旅行：30`）：その説明語を持つノードの件数
- **ノードにカーソルを当てる**：文書の概要（説明語・文書名・内容の一部）が表示される
- **ノードをクリック**：文書の全文とクエリ文書を並べて比較できる

---

## 注意事項

- 検索文書数を大きくすると処理時間が長くなります。生成中はロード画面が表示されます。
- 凡例に表示されるのはノード数が3件以上のカテゴリーのみです。
- ばねモデル法は計算負荷が高いため、他の手法より生成に時間がかかる場合があります。

### [2]：`/0_data`に検索対象の文章データを配置
検索対象の文章データを自分で作成して、`/0_data`に配置してください。ここに配置したデータがアプリ実行によって変更されることは無いです(サーバー側にコピーして使用するため)。
- `/0_data/doc.txt`
- `/0_data/wakachi.txt`
- `/0_data/uid.txt`

#### `/0_data/doc.txt`  
各文書のメタ情報を格納したファイルです。nnsk5.c の nnskReadName() で読み込まれます。カテゴリー番号はノードの色分けに直結します。1文書を必ず1行で記述し、途中の改行は除去してください。行番号が uid.txt および wakachi.txt と一致している必要があります。  
フォーマット（1行 = 1文書）  
```
{カテゴリー番号} {ファイル名またはタイトル}  
```

具体例
```
1 dokujo-tsushin-4778030.txt
2 it-life-hack-6289872.txt
2 it-life-hack-6292880.txt
3 kaden-channel-6218608.txt
```


####  `/0_data/wakachi.txt`  
doc.txtの各文書をMeCabで形態素解析し、単語をスペース区切りにしたテキストを格納したファイルです。mklbl.c の mklblReadValue() で読み込まれ、単語辞書（wid.txt）の構築とTF-IDF計算の基礎データとなります。検索精度を決定する最も重要なファイルです。　品詞の絞り込み（名詞・動詞のみ使用するなど）を行う場合は、全文書で統一したルールを適用してください。行番号が uid.txt および doc.txt と一致している必要があります。  

フォーマット（1行 = 1文書）
```
{単語1} {単語2} {単語3} ...
```  
具体例  
```
仕事 の ストレス 解消 に 効果 的 な 方法 と は ？ 毎日 の 業務 で 疲れ を 感じ て いる 方 へ ...
スマートフォン の 最新 モデル が 発売 。 価格 は 前 モデル より 1 万 円 安く ...
今季 の 映画 ランキング が 発表 さ れ た 。 1 位 に は 話題 の 邦画 が 輝き ...
```
  
  
####  `/0_data/uid.txt`  
各文書のメタ情報を格納したファイルです。nnsk5.c の nnskReadName() で読み込まれます。カテゴリー番号はノードの色分けに直結します。  

フォーマット（1行 = 1文書）
```
{カテゴリー番号} {ファイル名またはタイトル}
```  

具体例
```
1 dokujo-tsushin-4778030.txt
2 it-life-hack-6289872.txt
2 it-life-hack-6292880.txt
3 kaden-channel-6218608.txt
```

#### 3ファイルの対応関係
3ファイルは同じ行番号が同じ文書を指します。文書数をNとすると、それぞれ正確にN行である必要があります。
- uid.txt の3行目      → カテゴリー番号とファイル名
- doc.txt の3行目      → 同じ文書の原文
- wakachi.txt の3行目  → 同じ文書の分かち書き
  
クエリ文書をリクエストで送信すると、copyFile.c によってこれら3ファイルの先頭に1行追加されたコピーが生成され、検索処理はそのコピーを使用します。元ファイルは変更されません。

## 🔌 Apache CGI API仕様（`main.cgi`）
client から Apache サーバー（`main.cgi`）へ送るリクエストと、返却されるレスポンスの仕様です。

### エンドポイント
- URL: `http://localhost/cgi-bin/main.cgi`
- Method: `POST`
- Content-Type: `text/plain`
  - 実際の中身は JSON 文字列を送信

### リクエストボディ（JSON）
| フィールド名 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `name` | string | 必須 | クエリ文書名（例: `1 sample.txt`） |
| `normalText` | string | 必須 | クエリ文書の原文 |
| `wakachiText` | string | 必須 | 分かち書き済みテキスト |
| `networkType` | string | 必須 | 可視化アルゴリズム（`SE` / `MDS` / `CE` / `KK`） |
| `graphType` | string | 必須 | グラフ構築アルゴリズム（`MST` / `KNN` / `HML`） |
| `searchNum` | string | 必須 | 検索文書数（`50` / `100` / `150` / `200`） |

### レスポンスボディ（JSON）
| フィールド名 | 型 | 説明 |
| --- | --- | --- |
| `edges` | array | エッジ配列 |
| `nodes` | array | ノード配列 |

`edges` 要素:
- `x1`, `y1`（number）： エッジの始点ノードの2D座標（ピクセル値）
- `x2`, `y2`（number）：エッジの終点ノードの2D座標（ピクセル値）

`nodes` 要素:
- `category`（number）：説明語のカテゴリー番号（1以上）。同じ番号のノードは同じ説明語グループに属し、同色で描画される
- `keyword`（string）：そのノードの説明語（例：旅行、CM）。ノードがどのトピックで類似しているかを示す
- `id`（number）：元のデータセット内での文書ID（uid.txt の通し番号）
- `fileName`（string）：文書のファイル名（uid.txt に記載されたもの）
- `title`（string）：文書の本文テキスト。ホバー時の概要表示やクリック時の詳細表示に使用される
- `cx`, `cy`（number）：ノードの中心座標（ピクセル値）。描画領域（横1600px・縦700px）内に正規化済み
- `r`（number）：ノードの半径。クエリ文書（先頭ノード）は 12、それ以外は 6
- `color`（string, 例: `#E60012`）：ノードの塗り色（HEXカラーコード）。category の値に応じて動的に生成される

### 軽いリクエストサンプル
```bash
curl -X POST "http://localhost/cgi-bin/main.cgi" \
  -H "Content-Type: text/plain" \
  --data-raw '{"name":"1 sample.txt","normalText":"検索したい文章です。","wakachiText":"検索 したい 文章 です 。","networkType":"KK","graphType":"KNN","searchNum":"50"}'
```

### 軽いレスポンスサンプル
```json
{
  "edges": [
    { "x1": 231.51, "y1": 114.61, "x2": 390.91, "y2": 514.59 }
  ],
  "nodes": [
    {
      "category": 1,
      "keyword": "サンプル",
      "id": 1,
      "fileName": "sample.txt",
      "title": "本文の要約テキスト",
      "cx": 231.51,
      "cy": 114.61,
      "r": 12,
      "color": "#E60012"
    }
  ]
}
```

### CGI入力サイズ制限（Cコード由来）
`main.cgi` は C 言語実装のため、実質的に以下のサイズ制限があります。

| 対象 | 実質上限 | 根拠 |
| --- | --- | --- |
| HTTPボディ(JSON全体) | 固定上限なし（メモリ依存） | `CONTENT_LENGTH` 分を `malloc` して `fgets` で読込 |
| `name` | 4095 bytes 以下推奨 | 後段のノード読込で `fileName[4096]` に `%4095s` で読込 |
| `normalText`（1行） | 262143 bytes 以下推奨 | 後段のノード読込で `context[262144]` に `%262143s` で読込 |
| `wakachiText` の各トークン | 511 bytes 以下推奨 | 後段のノード読込で `keyword[512]` に `%511s` で読込 |

補足:
- 上限超過時は、`500 Internal Server Error` や JSON 破損、CGI 異常終了の原因になります。
- 本リポジトリの client には、上記制限に合わせた送信前バリデーションを実装済みです。

### バッファサイズ変更に関する補足
本リポジトリでは、文字列処理の安全性を高めるために、固定長バッファの一部を拡張/可変化しています。

- 変更した内容:
  - 文字列の読み込みバッファサイズ
  - 文字列読み込み時の幅指定（`%s` の安全化）
- 変更していない内容:
  - TF-IDF、類似度計算、配置計算などの数値計算式
  - 可視化アルゴリズム（`SE` / `MDS` / `CE` / `KK`）の計算ロジック

そのため、通常サイズの入力では計算結果は基本的に従来と同一です。  
一方で、従来はバッファ超過で不安定化していた長い入力では、挙動が変わる（異常終了しにくくなる、結果が安定する）可能性があります。
