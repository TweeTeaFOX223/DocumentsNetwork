# 📄 DocumentsNetwork  

**「DocumentsNetwork＝類似貢献度に基づく文書検索結果の可視化分析ツール」** は、クエリ文書に似た文書を検索し、その結果をネットワーク図として可視化するアプリケーションです。

単なる類似度スコアによる順位付けにとどまらず、「**どの単語がどれくらいクエリとの類似に貢献しているか**」を単語ごとに数値化した**類似貢献度ベクトル**を用いて文書間のグラフを構成します。各文書には貢献度が最も高い単語が**説明語**として付与され、同じ説明語を持つ文書グループは同じ色で表示されるため、検索結果全体が「どんなテーマの文書が多いか」「どんなキーワードで似ているか」を一目で把握できます。

### 🔬 研究の新規性（新しく提案している手法）

#### １：類似貢献度ベクトルを用いた可視化分析法
従来の文書検索は「クエリ文書にどれくらい似ているか」というスコア1つで順位付けするのみでした。本研究では、各検索結果文書について「**どの単語がどれくらいクエリとの類似に貢献しているか**」を単語ごとに数値化した「類似貢献度ベクトル」を新たに定義・構築します。このベクトルを用いてK最近傍グラフを構成し、各ノードに**説明語**（類似貢献度が最大の単語）を付与してグループ分け・配色する可視化手法を提案しています。検索結果全体を「どんなテーマ・単語でクエリに似ているか」という観点でひと目で把握できる点が新しい貢献です。

#### ２：グラフ可視化結果の定量評価法
グラフの見やすさはこれまで目視による定性評価に頼るしかありませんでしたが、本研究では「良いグラフ」の基準を以下の2つに定義し、**自動で数値評価できる手法**を新たに提案しています。

- **エッジ長の変動係数（CV値）**：エッジ長のばらつきを数値化し、隣接ノードが適切な距離に配置されているかを評価
- **重複ノード数**：重なっているノードのペア数を数値化し、ホバー・クリック操作のしやすさを評価

livedoorニュースコーパス（約7,300件）を使った実験で、この定量評価が人間の目視による定性評価と一致することを検証し、評価手法の妥当性を確認しています。

## 🎯 アプリ概要

### このツールは何をするもの？
「この文書に似た文書を探したい」——そんなとき、検索結果が100件ずらっとリスト表示されても、全体像はなかなか把握しにくいものです。
このツールは、文書検索の結果をグラフ（ネットワーク図）として視覚的に表示する可視化ブラウジングツールです。似ている文書どうしが近くに集まり、色分けされて表示されるので、「どんなテーマの文書が多いか」「どんなキーワードで似ているか」が一目でわかります。

### どんな仕組みで動いているのか？

#### １：「どの単語で似ているか」を数値化する（類似貢献度ベクトル）
通常の検索では「このクエリ文書にどれくらい似ているか」というスコア1つで順位付けをします。このツールでは一歩進んで、「どの単語がどれくらいクエリとの類似に貢献しているか」 を単語ごとに計算します。これを「類似貢献度ベクトル」と呼びます。
たとえばクエリが「ゆるキャラのCMについての記事」なら、ある検索結果文書について「CM：40%、車：30%、キャンペーン：15%…」のように、各単語の貢献割合がわかります。

#### ２：貢献度をもとにグラフ（ネットワーク）を作る（Graph設定）
類似貢献度ベクトルが近い文書同士をエッジ（線）で繋ぎ、ネットワーク図を構成します。エッジの張り方（グラフ構成法）はK最近傍法（KNN）・最小全域木（MST）・MST-hML（ハイブリッド）の3種類から選べます。各手法の詳細は後述の「[2. Graph](#2-graphグラフ構成法)」を参照してください。クラスター構造を把握しやすい**K最近傍法（KNN）**が推奨です。

#### ３：グループを色と「説明語」で表示する
各文書について、類似貢献度がもっとも高い単語を「説明語」として選びます。同じ説明語を持つ文書グループは同じ色で表示され、グラフ上部にはグループ名と件数が一覧表示されます。
たとえば、クエリにゆるキャラのCM記事を指定すると：  
- 🟠 CM（42件）
- 🟢 店（30件）
- 🔵 クルマ（15件）

のように、検索結果全体がどんなテーマに分布しているかが直感的にわかります。

#### ４：グラフを2次元空間に見やすく配置する（Visual設定）
グラフの構造が決まったら、次はそれを画面上にどう配置するかです。ノードの座標を決めるレイアウトアルゴリズムを4種類から選べます（スペクトラル法・多次元尺度法・クロスエントロピー法・**ばねモデル法**）。各手法の詳細は後述の「[1. Visual](#1-visualグラフ可視化手法)」を参照してください。実験では**ばねモデル法**が最も高品質なグラフを生成することが確認されています。

#### ５：検索する文書数を決める（Search設定）
クエリ文書とデータセット内の全文書を比較し、類似度の高い順に何件をグラフに表示するかを指定します。50・100・150・200件の4段階から選べます。各設定の詳細は後述の「[3. Search](#3-search検索文書数)」を参照してください。論文の実験でも**100件**が視認性と情報量のバランスが最も良いことが確認されており、推奨設定です。

#### ６：ノードをホバー・クリックして文書を確認
グラフ上の各丸（ノード）にマウスを乗せると、その文書のタイトルや内容の概要が表示されます。クリックすると全文を確認でき、クエリ文書と並べて比較することもできます。  

### 可視化の品質をどう評価しているの？（定量評価手法）
グラフの見やすさは可視化アルゴリズムによって大きく変わります。このツールの研究では、「良いグラフとは何か」を以下の2つの基準で定義し、数値で自動評価する手法も提案しています。

- 基準1：隣接ノードが離れすぎていないか（エッジ長の変動係数）
エッジ（文書間をつなぐ線）の長さが均一であるほど、隣同士の文書が適度な距離に配置され、ホバーしやすくなります。エッジ長のばらつきを「変動係数（CV値）」で数値化し、この値が小さいほど良い可視化と評価します。  
- 基準2：ノードが重なっていないか（重複ノード数）
複数のノードが重なって表示されると、クリックやホバーができなくなります。重なりのあるノードのペア数を数えることで、重なりのなさを数値化します。この値が小さいほど良い可視化です。
- 評価実験の結果
livedoorニュースコーパス（約7,300件）を使った実験で、4種類のグラフ描画アルゴリズム（スペクトラル法・多次元尺度法・クロスエントロピー法・ばねモデル法）を比較しました。
ばねモデル法が2つの基準をともに高水準で満たし、最も見やすいグラフを生成することが確認されました。この定量評価の結果は、人間が目視で確認した定性評価とも一致しており、提案した評価手法の妥当性が検証されています。
このツールでもデフォルトの可視化アルゴリズムにばねモデル法を採用しています。

## 🚀 アプリの起動方法

### 形態素解析に使用するMeCab
- 本アプリの MeCab 呼び出しは、Node.js の `mecab-async` パッケージを使用しています。
- `mecab-async` は MeCab 本体を内部に同梱しないため、システムに MeCab のインストールが必要です。
- Docker 利用時は、MeCab 本体のインストールをコンテナ内部で実行しています（`settings/DockerfileMeCab`）。
- 使用辞書はデフォルト設定で、`mecab-ipadic-utf8` を使用しています。

### [2]：`/0_data`に検索対象の文章データを配置
検索対象の文章データを自分で作成して、`/0_data`に配置してください。ここに配置したデータがアプリ実行によって変更されることは無いです(サーバー側にコピーして使用するため)。
- `/0_data/doc.txt`
- `/0_data/wakachi.txt`
- `/0_data/uid.txt`

#### `/0_data/doc.txt`  
各文書の原文（全文テキスト）を格納するファイルです。1文書を必ず1行で記述し、文書途中で改行しないでください。行番号が `uid.txt` および `wakachi.txt` と一致している必要があります。  
フォーマット（1行 = 1文書）  
```
{文書の原文}
```

具体例
```
仕事のストレスを減らすために、睡眠と運動を見直すことが重要です。
スマートフォンの最新モデルが発売され、処理性能と省電力性能が向上しました。
今季の映画ランキングが発表され、話題作が上位に入りました。
電気自動車の普及が進み、充電インフラ整備が課題となっています。
```


####  `/0_data/wakachi.txt`  
doc.txtの各文書をMeCabで形態素解析し、単語をスペース区切りにしたテキストを格納したファイルです。mklbl.c の mklblReadValue() で読み込まれ、単語辞書（wid.txt）の構築とTF-IDF計算の基礎データとなります。検索精度を決定する最も重要なファイルです。　品詞の絞り込み（名詞・動詞のみ使用するなど）を行う場合は、全文書で統一したルールを適用してください。行番号が uid.txt および doc.txt と一致している必要があります。  

フォーマット（1行 = 1文書）
```
{単語1} {単語2} {単語3} ...
```  
具体例  
```
仕事 の ストレス 解消 に 効果 的 な 方法 と は ？ 毎日 の 業務 で 疲れ を 感じ て いる 方 へ ...
スマートフォン の 最新 モデル が 発売 。 価格 は 前 モデル より 1 万 円 安く ...
今季 の 映画 ランキング が 発表 さ れ た 。 1 位 に は 話題 の 邦画 が 輝き ...
```
  
  
####  `/0_data/uid.txt`  
各文書のメタ情報を格納したファイルです。nnsk5.c の nnskReadName() で読み込まれます。カテゴリー番号はノードの色分けに直結します。  

フォーマット（1行 = 1文書）
```
{カテゴリー番号} {ファイル名またはタイトル}
```  

具体例
```
1 dokujo-tsushin-4778030.txt
2 it-life-hack-6289872.txt
2 it-life-hack-6292880.txt
3 kaden-channel-6218608.txt
```

#### 3ファイルの対応関係
3ファイルは同じ行番号が同じ文書を指します。文書数をNとすると、それぞれ正確にN行である必要があります。
- uid.txt の3行目      → カテゴリー番号とファイル名
- doc.txt の3行目      → 同じ文書の原文
- wakachi.txt の3行目  → 同じ文書の分かち書き
  
クエリ文書をリクエストで送信すると、copyFile.c によってこれら3ファイルの先頭に1行追加されたコピーが生成され、検索処理はそのコピーを使用します。元ファイルは変更されません。

### [3_A]：Dockerを使用して各サーバーを起動(簡単・ストレージ消費大)
`settings`にあるDockerFileに基づき、Dockerコンテナのビルド＆各サーバーの起動をします。`cgi` サーバーは起動時に、ローカルの`0_data`から `uid.txt` / `doc.txt` / `wakachi.txt` の3ファイルだけをコンテナ内へコピーして使用します。  
```
docker compose up
```

#### 3_A補足：コンテナ作成済みで、変更後に反映する操作
`docker compose up` を一度実行済みの場合、プログラムの変更箇所ごとに必要な操作は以下です。

- client（`client/index.html` などフロントファイル）
  - `client` は bind mount（`./client -> /projects/client`）なので、通常はファイル保存後にブラウザ再読み込みで反映されます。
  - サービスを再起動したい場合:
  ```
  docker compose restart client
  ```

- mecab（`server-mecab/*.js` など）
  - `mecab` はイメージ内の `/projects/server-mecab` を実行しているため、コード変更は再ビルドが必要です。
  ```
  docker compose up -d --build mecab
  ```

- C CGI（`server-cgi-bin/c_file/*.c` や `settings/DockerfileCgi`）
  - `main.cgi` は Docker イメージ作成時に C をコンパイルして生成しているため、Cコード変更は再ビルドが必要です。
  ```
  docker compose up -d --build cgi
  ```

- `0_data`（`uid.txt` / `doc.txt` / `wakachi.txt`）
  - `cgi` 起動時にコンテナ内へコピーする仕様のため、`0_data` を変更したら `cgi` の再作成（または再起動）で反映します。
  ```
  docker compose up -d --force-recreate cgi
  ```

補足:
- **全部まとめて更新する場合は以下で再ビルド/再作成できます。**
```
docker compose up -d --build
```

  
※DockerはPCのストレージの消費量が大きいです。ストレージ消費を少なく済ませたい場合は、3_Bの方に書いてある方法を使ってください。

## ⚙️ アプリ画面の設定・操作ガイド

**Visual・Graph・Search** の3項目をそれぞれ1つ選択し、実行してください。  
  
### 1. Visual（グラフ可視化手法）

ノードを2次元空間に配置する際のレイアウトアルゴリズムを選択します。

| 選択肢                   | 説明                                                                           | 特徴                                                             |
| ------------------------ | ------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| **スペクトラル法**       | 隣接ノードの座標が近くなるよう配置する手法                                     | 計算が速いが、ノードが重なりやすく視認性が低下しやすい           |
| **多次元尺度法**         | 高次元空間での複数観点の類似性を保ちながら低次元に射影する手法                 | 全体的な距離構造を反映しやすい                                   |
| **クロスエントロピー法** | 隣接ノードを非隣接ノードより近くに配置するよう交差エントロピーを最小化する手法 | ノードの重なりを抑えやすいが計算コストが高い                     |
| **ばねモデル法**         | 全エッジをばねとみなし、ノード間の最短パス長を自然長として配置する手法         | **推奨**。ノードの重なりが最も少なく、エッジ長のばらつきも小さい |

> **推奨設定：ばねモデル法**
> エッジ長の均一性・ノードの重なりにくさの両面で最も高品質なグラフが得られます。

---

### 2. Graph（グラフ構成法）

文書間のエッジ（繋がり）をどのように構築するかを選択します。

| 選択肢                | 説明                                                                                                     | 特徴                                                                                 |
| --------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **最小全域木（MST）** | コサイン類似度が最大となるエッジを優先的に選び、全ノードを連結する最小本数のエッジでグラフを構成する手法 | エッジ数が少なくツリー状になる。全体構造は把握しやすいが、密な部分構造の視認性は低い |
| **K最近傍法（KNN）**  | 各ノードに対して類似度の高い近傍ノードとのエッジを追加し、グラフ全体が連結になるまで繰り返す手法         | **推奨**。MSTより密なグラフが得られ、類似文書のクラスター構造を視覚的に把握しやすい  |
| **MST-hML**           | MSTを骨格として構築した後、コサイン類似度が特に高いペアのエッジをさらに追加するハイブリッド手法          | MSTの疎さを補いつつ、高類似度の関係を強調できる                                      |

> **推奨設定：K最近傍法**
> クラスター構造や密な類似関係の把握に最も適しています。

---

### 3. Search（検索文書数）

クエリ文書（アップロードした文書）と、データセット内の全文書を比較し、類似度の高い文書を上位から何件グラフに表示するかを事前に指定する設定です。この件数を決めてから計算が開始されるため、実行後に件数だけを変更することはできません。件数を変えたい場合は設定を変え直して再度Submitしてください。

| 選択肢    | 説明                                                                                         |
| --------- | -------------------------------------------------------------------------------------------- |
| **50件**  | 文書数が少ないためグラフはシンプルになるが、密な部分構造が見えにくい場合がある               |
| **100件** | **推奨**。視認性と情報量のバランスが最も良い                                                 |
| **150件** | やや多めの文書を俯瞰したい場合に使用                                                         |
| **200件** | 多数の文書を一覧できるが、元の文書集合に類似文書が少ない場合は関連性の薄い文書が混入しやすい |

> **推奨設定：100件**
> 件数を増やすほどクエリとの類似度が低い文書まで含まれるようになります。データセットにクエリと似た文書が少ない場合、200件を指定すると関連性の薄い文書がグラフの外縁部に多数出現することがあります。また件数が多いほど処理時間も長くなります。

---

### 推奨設定の組み合わせ

特に理由がない場合は以下の設定をお試しください。

```
Visual  : ばねモデル法
Graph   : K最近傍法
Search  : 100件
```

### グラフの見方

- **赤い大きな丸**：アップロードしたクエリ文書
- **色付きの小さな丸**：検索結果の類似文書（同じ色のノードは同じ「説明語」でクエリに類似していることを示す）
- **グラフ上部の凡例**（例：`● 旅行：30`）：その説明語を持つノードの件数
- **ノードにカーソルを当てる**：文書の概要（説明語・文書名・内容の一部）が表示される
- **ノードをクリック**：文書の全文とクエリ文書を並べて比較できる

---

### 注意事項

- 検索文書数を大きくすると処理時間が長くなります。生成中はロード画面が表示されます。
- 凡例に表示されるのはノード数が3件以上のカテゴリーのみです。
- ばねモデル法は計算負荷が高いため、他の手法より生成に時間がかかる場合があります。

## 🔌 開発者向け情報

### Apache CGI API仕様（`main.cgi`）
client から Apache サーバー（`main.cgi`）へ送るリクエストと、返却されるレスポンスの仕様です。

#### エンドポイント
- URL: `http://localhost/cgi-bin/main.cgi`
- Method: `POST`
- Content-Type: `text/plain`
  - 実際の中身は JSON 文字列を送信

#### リクエストボディ（JSON）
| フィールド名  | 型     | 必須 | 説明                                             |
| ------------- | ------ | ---- | ------------------------------------------------ |
| `name`        | string | 必須 | クエリ文書名（例: `1 sample.txt`）               |
| `normalText`  | string | 必須 | クエリ文書の原文                                 |
| `wakachiText` | string | 必須 | 分かち書き済みテキスト                           |
| `networkType` | string | 必須 | 可視化アルゴリズム（`SE` / `MDS` / `CE` / `KK`） |
| `graphType`   | string | 必須 | グラフ構築アルゴリズム（`MST` / `KNN` / `HML`）  |
| `searchNum`   | string | 必須 | 検索文書数（`50` / `100` / `150` / `200`）       |

#### レスポンスボディ（JSON）
| フィールド名 | 型    | 説明       |
| ------------ | ----- | ---------- |
| `edges`      | array | エッジ配列 |
| `nodes`      | array | ノード配列 |

`edges` 要素:
- `x1`, `y1`（number）： エッジの始点ノードの2D座標（ピクセル値）
- `x2`, `y2`（number）：エッジの終点ノードの2D座標（ピクセル値）

`nodes` 要素:
- `category`（number）：説明語のカテゴリー番号（1以上）。同じ番号のノードは同じ説明語グループに属し、同色で描画される
- `keyword`（string）：そのノードの説明語（例：旅行、CM）。ノードがどのトピックで類似しているかを示す
- `id`（number）：元のデータセット内での文書ID（uid.txt の通し番号）
- `fileName`（string）：文書のファイル名（uid.txt に記載されたもの）
- `title`（string）：文書の本文テキスト。ホバー時の概要表示やクリック時の詳細表示に使用される
- `cx`, `cy`（number）：ノードの中心座標（ピクセル値）。描画領域（横1600px・縦700px）内に正規化済み
- `r`（number）：ノードの半径。クエリ文書（先頭ノード）は 12、それ以外は 6
- `color`（string, 例: `#E60012`）：ノードの塗り色（HEXカラーコード）。category の値に応じて動的に生成される

#### 軽いリクエストサンプル
```bash
curl -X POST "http://localhost/cgi-bin/main.cgi" \
  -H "Content-Type: text/plain" \
  --data-raw '{"name":"1 sample.txt","normalText":"検索したい文章です。","wakachiText":"検索 したい 文章 です 。","networkType":"KK","graphType":"KNN","searchNum":"50"}'
```

#### 軽いレスポンスサンプル
```json
{
  "edges": [
    { "x1": 231.51, "y1": 114.61, "x2": 390.91, "y2": 514.59 }
  ],
  "nodes": [
    {
      "category": 1,
      "keyword": "サンプル",
      "id": 1,
      "fileName": "sample.txt",
      "title": "本文の要約テキスト",
      "cx": 231.51,
      "cy": 114.61,
      "r": 12,
      "color": "#E60012"
    }
  ]
}
```

### Request/Response Log 機能（client）
client 画面下部の `Request/Response Log` では、送受信データと生成情報を確認・保存できます。

- 表示される主な項目:
  - `Request payload`（送信した JSON）
  - `Response payload`（受信したレスポンス）
  - `Graph generation`（生成時間・選択オプション）
  - `Target categories (from response)`（レスポンス `nodes` から算出したカテゴリ数とカテゴリ名一覧）
  - `Error`（HTTPエラーや JSON パースエラーなど）
- 保存機能:
  - `Save latest`: 最新1件のログを JSON で保存
  - `Save all`: これまでの全ログを JSON 配列で保存
- 保存JSONに含まれる代表フィールド:
  - `timestamp`
  - `request`
  - `response`
  - `generation`（`fileName`, `visual`, `graph`, `search`, `elapsedMs`, `elapsedSeconds`）
  - `error`

### 全オプション実験機能（client）
`Request/Response Log` 下部の実験ボタンから、アップロード中のクエリ文書に対して全組み合わせ実行ができます。

- 実行対象:
  - `Visual` 4種（`SE` / `MDS` / `CE` / `KK`）
  - `Graph` 3種（`MST` / `KNN` / `HML`）
  - `Search` 4種（`50` / `100` / `150` / `200`）
  - 合計 `48` 通り（4 × 3 × 4）
- 実行前の確認:
  - 開始時に「実験用機能で時間がかかる」旨の確認ダイアログを表示
- 実行中UI:
  - 画面上部に進捗ポップアップを表示（完了数、現在の組み合わせ）
  - `中止` ボタンで中断リクエスト可能（現在処理完了後に停止）
- 出力:
  - ダウンロードファイルは `実験_{入力ファイル名}_{日時}.zip`
  - ZIP内は組み合わせごとのディレクトリ（例: `SE_KNN_100件_日時`）
  - 各ディレクトリに以下を保存:
    - `request-response-log.json`
    - `graph.svg`
- ログ反映:
  - 各組み合わせごとに `Graph generation`（時間・オプション）を更新
  - `request-response-log.json` に生成時間情報を含めて保存

### CGI入力サイズ制限（Cコード由来）
`main.cgi` は C 言語実装のため、実質的に以下のサイズ制限があります。

| 対象                       | 実質上限                   | 根拠                                                      |
| -------------------------- | -------------------------- | --------------------------------------------------------- |
| HTTPボディ(JSON全体)       | 固定上限なし（メモリ依存） | `CONTENT_LENGTH` 分を `malloc` して `fgets` で読込        |
| `name`                     | 4095 bytes 以下推奨        | 後段のノード読込で `fileName[4096]` に `%4095s` で読込    |
| `normalText`（1行）        | 262143 bytes 以下推奨      | 後段のノード読込で `context[262144]` に `%262143s` で読込 |
| `wakachiText` の各トークン | 511 bytes 以下推奨         | 後段のノード読込で `keyword[512]` に `%511s` で読込       |

補足:
- 上限超過時は、`500 Internal Server Error` や JSON 破損、CGI 異常終了の原因になります。
- 本リポジトリの client には、上記制限に合わせた送信前バリデーションを実装済みです。

### バッファサイズ変更に関する補足
この変更は、長文入力時の不安定動作（バッファ超過、JSON破損、CGI異常終了）を抑えるために行いました。  
従来は固定長配列に対して読み込み幅の管理が十分でない箇所があり、入力サイズ次第で処理が壊れるリスクがありました。

1. 何を変更したか
- 文字列を受け取るバッファのサイズを拡張、または必要箇所を可変長化
- `scanf`/`sscanf` 系の `%s` 読み込みに幅指定を追加し、配列境界を超えないように修正
- `CONTENT_LENGTH` に基づくリクエスト読込処理との整合を取り、受信サイズと内部バッファ制約のギャップを縮小

2. なぜ変更したか
- C言語の固定長バッファは、上限超過時にメモリ破壊や不正JSON出力を引き起こしやすいため
- フロント側でバリデーションを入れていても、サーバ側で防御しないと異常系が残るため
- 入力データの実運用サイズに対して、より安全に失敗/処理継続できる状態にするため

3. 変更の効果
- 長い入力でも CGI が異常終了しにくくなり、レスポンスの安定性が向上
- サイズ超過時の挙動が「壊れる」より「安全に失敗する」方向に改善
- 将来の上限調整時も、コード修正範囲を局所化しやすくなる

4. 変更していない範囲（重要）
- TF-IDF、類似度計算、ノード配置などの数値計算式
- 可視化アルゴリズム（`SE` / `MDS` / `CE` / `KK`）の計算ロジック

そのため、通常サイズの入力に対しては計算結果は基本的に従来と同等です。  
差が出るのは主に、従来はバッファ制約に近く不安定だった境界ケース（非常に長い入力）です。

### カテゴリ上限撤廃と色生成の動的化（実装済み）
従来実装では、カテゴリ番号の採番に上限（実質24カテゴリ）があり、カテゴリ数が増える入力で情報が潰れる可能性がありました。  
また、色も固定配列の循環参照だったため、カテゴリ数が増えると同色再利用が早期に発生し、視認性が低下していました。  
これを解消するため、以下の実装変更を行っています。

1. `nnsk5.c` のカテゴリ上限を撤廃
- 変更内容: `if(i < 24) i++;` を `i++;` に変更
- 目的: 入力データに含まれるカテゴリ数をそのまま扱えるようにする
- 効果: カテゴリ数が24を超えるケースでも、カテゴリが丸められずに採番される

2. `commonNodeColor`（固定色配列）を廃止
- 変更内容: 静的な25色配列を削除し、`generateNetwork.c` から色配列依存を除去
- 目的: 配列長に依存した色割当をやめ、カテゴリ数の増加に追従できる構造にする
- 効果: 色割当の制約が「配列サイズ」ではなく「生成ロジック」に一本化される

3. `SE` / `MDS` / `CE` / `KK` の色決定を動的生成に統一
- 変更内容: 各モジュール内で `category` から HEX 色を生成する関数を導入し、`nodeColor[(category-1)%N]` を撤去
- 目的: アルゴリズムごとに同じ方針で色を決め、カテゴリ数が増えても破綻しないようにする
- 効果: 大カテゴリ数の入力でも配色処理が継続し、描画時の一貫性を維持できる

補足:
- 本変更は「カテゴリ採番と色割当」の実装改善であり、TF-IDF・類似度・座標計算などの数値計算式は変更していません。
